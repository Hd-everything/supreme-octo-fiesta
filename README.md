# Vyntra cloud renderer

This directory contains the FFmpeg worker used by the one-shot GitHub Actions workflow. FFmpeg must not run inside a Supabase Edge Function.

## Current supported render plan

The worker supports photos and the editing operations below. Unsupported edits are rejected rather than silently omitted.

- Ordered video clips and still photos (`png`, `jpg`, `jpeg`, `webp`), with trim points, 90-degree rotation, reverse, speed changes, freeze frames, per-clip volume, audio fades, and audio cleanup.
- Cut, fade, fade-to-black, dissolve, wipe-left, and slide-right transitions, with audio crossfades.
- Per-clip brightness, contrast, saturation, keyframed adjustments, and built-in looks: flash, shake, blur, glitch, phonk, grayscale, negative, cinematic, moody, vivid, dramatic, vintage, fade, night, sunset, noir, soft, and dreamy.
- Original, 9:16, 16:9, 1:1, 4:5, 3:4, 4:3, and 21:9 framing.
- Optional soundtrack mixing, timed text overlays, and positioned timed image overlays.
- 24, 25, 30, 50, or 60 fps output; 720p through 6K output and opt-in 8K; H.264 and H.265 when `libx265` is available.
- ffprobe output metadata validation plus a full decode pass before completion.
- Private storage object paths and service-role credentials kept on the server.

Each export is limited to 24 clips, 180 seconds of rendered timeline, and 200 MiB of combined source media. Sources larger than 48 MB are uploaded as byte-exact parts; each Storage object remains below 50 MB. AI restoration, body tracking, background removal, optical-flow slow motion, animated sticker packs, and advanced masks are not implemented. 8K is disabled by default, has a worker RAM/disk guard, and must not be exposed unless the deployment is explicitly enabled and passes an actual 7680x4320 decode test.

## Deploy

GitHub Actions can run one job per workflow run using `.github/workflows/status-hd-render.yml`. Configure repository Actions secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` for the primary project that owns Auth, the job table, source uploads, and the Edge Function. The secondary output project URL is `https://vfaakmxoeflzedwidlcl.supabase.co`. Add its service-role key as `VYNTRA_OUTPUT_SUPABASE_SERVICE_ROLE_KEY` in both GitHub Actions repository secrets and the primary project's Edge Function secrets. The Edge Function creates a private `vyntra-exports` bucket with a 50 MB per-object limit on first use. New jobs route only their output to the second project; source media and the render queue stay in the primary project. Existing jobs without a route marker remain on the primary project. If a secondary output upload fails with a capacity response (HTTP 402, 413, 507, or an explicit storage-quota error), the worker removes partial secondary output, switches the job's recorded route to primary, and retries the complete output there. The Edge Function then signs and cleans up the output from primary. Other upload errors do not trigger fallback. If the secondary key is absent, output storage falls back to the primary project. Supabase Free Storage quota is shared across projects in the same organization; this separate-organization project has its own 1 GB quota. Supabase currently allows two active Free projects across organizations. Never put service-role secrets in Flutter, logs, or committed files. In the primary project's Edge Function secrets, also configure `GITHUB_RENDER_DISPATCH_TOKEN` as a fine-grained token scoped only to this repository with Actions/Contents permissions required to dispatch repository events, and `GITHUB_RENDER_REPOSITORY=Hd-everything/supreme-octo-fiesta`. Set `VYNTRA_RENDER_WORKER_READY=true` only after a real render test succeeds. The workflow uses a one-shot worker and does not run a permanent polling server.

Source media remains in the primary project's private `vyntra-media` bucket. New rendered outputs use the configured secondary project's private `vyntra-exports` bucket; if a secondary upload returns a capacity response, the worker retries the complete output in the primary bucket and records that route for download and cleanup. Without secondary configuration, outputs remain in primary. Source files over 48 MB and rendered MP4s over 48 MB are split into ordered 48,000,000-byte objects and reconstructed byte-for-byte; Supabase Free's 50 MB per-object limit is respected without changing media quality. The default per-export limit is 200,000,000 bytes (configurable with `VYNTRA_MAX_OUTPUT_BYTES`), and the combined source-media limit is 200 MiB per job. These are per-job safety caps, not storage quotas. Each Free organization has 1 GB shared Storage quota across its projects. Temporary source/output files are deleted after the app verifies delivery and acknowledges the job. If a user never completes delivery, cleanup requires retry/expiry handling. Smaller MP4s remain a single object for compatibility.

Supabase Storage limits and egress vary by plan. Status HD cloud requests are capped at 50 MiB per uploaded object and 180 seconds total video duration; the worker re-checks the actual downloaded file size and probes media duration independently. The workflow has a 25-minute timeout. 4K software encoding can be slow and consumes CPU, disk, and egress. 8K is disabled by default due to high memory, CPU, and storage demands. GPU is not required for ordinary FFmpeg encoding.

## Important integration status

The Flutter client establishes a Supabase anonymous guest session in the background (no sign-in UI), validates 50 MiB / 180-second limits, uploads each referenced source asset to a guest-scoped object path, rewrites local paths in the project snapshot, and calls the Edge Function. The Edge Function authenticates the user JWT, limits active jobs, validates owner-scoped paths, and dispatches GitHub without exposing its token. Anonymous sign-ins must be enabled in Supabase Auth. The worker intentionally rejects local paths and cross-guest object paths. After the user has configured the required secrets, test a short sample end-to-end. The client acknowledges a successful local download so the Edge Function can delete temporary input/output objects. Also configure a scheduled cleanup for abandoned jobs and test that failure path before enabling public use. GitHub Actions is a temporary job runner, not an always-on server. The current worker uses FFmpeg quality filters; a dedicated AI restoration model is not yet wired into this pipeline.
